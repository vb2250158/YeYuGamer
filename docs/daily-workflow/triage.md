# 故障归因与证据清单

按 [每日主流程](../daily-workflow.md) 使用。先核实官方最新版本和已有修复，再排查 YeYu，最后确认是否需要上游补丁。

## 证据包

本机保存于 `.cache/verification/<日期-任务>/`；原始日志仍由 Manager 保存在本机运行目录，不放公开 Git。

| 内容 | 必须回答的问题 |
| --- | --- |
| 版本与来源 | 当前实际执行什么 commit、release、依赖和资源？官方最新版何时查的？ |
| 范围与轮次 | 哪个账号、游戏日、RunAttempt、勾选步骤失败？是否混用了历史结果？ |
| 复现条件 | 什么输入/配置/场景触发？预期与实际分别是什么？复现次数及条件有何变化？ |
| 首个错误 | 第一处异常在哪里？后续错误是否只是清理、传输或截图失败？ |
| 配置与调用 | 注入的字段是否属于该上游版本？默认值、参数、账号、步骤映射是否正确？ |
| 控制与观察 | 启动绑定是否正确？观察器是否原样返回/抛错？有无日志丢失或协议异常？ |
| 对照验证 | 原版上游的最小测试/离线重放能否复现？与受控接入结果有何区别？ |
| 修复验证 | 修复前失败、修复后通过的具体测试及产品实跑结果是什么？ |

只读诊断优先用 WebGUI、CLI、受支持 API 和工件。确需存储调查时只用项目支持的只读诊断，不修改 DB；版本相关表名不能直接从旧案例照抄。`todo` 全绿、进程退出和整项失败之间的差异要追到本轮终态，不靠硬编码状态规则重判。

## 责任判断

- YeYu：正确官方输入能通过，但接入注入/映射、观察、生命周期或汇总存在可定位缺陷；修复对应代码。
- 上游：正确输入在所查上游版本仍能复现，根因位于官方源码，并已排除接入副作用；准备上游修复。
- 环境/客户端：官方更新、依赖、资源、权限或客户端状态导致；按实际原因恢复，不修改业务终态。
- 能力缺失：上游无对应入口或未支持所选范围；记录缺口，不能靠开启 YeYu 能力开关伪造支持。
- 待定：缺日志或未排除其他原因；补证据，暂不发送确定归因的 PR。

不要为了对照裸启游戏绕开项目入口。优先用上游离线测试隔离业务逻辑；需要现场对照时通过受支持候选和 WebGUI，固定配置与版本，并说明无法控制的场景差异。给“原因已确认”提供可审查证据，不声称排除了所有未知因素。

对外材料移除账号、UID、昵称、凭据、Cookie、Token、邮件地址、私有路径、聊天内容和截图中的个人信息。保留理解问题所需的堆栈、版本和步骤；检查脱敏后仍能复现。日志增多不是证据更强，禁止反复输出完整配置和密钥。
