# 上游修复与 PR

先完成 [每日主流程](../daily-workflow.md) 的版本核实与 [归因](triage.md)，确认缺陷在工具而非 YeYu。仅按实际任务授权对外提交。

1. 查询官方最新 release、默认分支和相关 open/closed issue、PR；记录链接、commit 与查询时间，避免重复修复。
2. 在项目 `.cache` 对应候选目录准备独立上游 checkout，保留已有补丁和用户配置。读取上游 AGENTS、贡献说明及测试要求；不猜默认分支或 fork 所有人。
3. 用最小失败测试/复现固定根因，修改上游源码，运行相关测试。不要把游戏逻辑修复植入 YeYu 观察器；不能靠吞异常或改失败标签获得成功。
4. 检查 diff、依赖/生成物与敏感信息。使用独立分支提交，仅包含这个问题的必要改动；Codex 默认分支前缀为 `codex/`，明确的仓库约定优先。
5. 推送 fork 并创建 PR；已有同一修复 PR 时更新它，避免重复。正文通过结构化参数或 UTF-8 文件传入 `--body-file`，不拼接 Shell 字符串。
6. 核对 PR URL、base/head 和 CI。失败先读日志，处理本次引入的问题；无法本机验证的部分如实列明。只有已经观察到的审查和 CI 状态可报告。
7. 将候选版本和 PR 关联写入本机调查记录，经正常发布/绑定后从 WebGUI 继续每日；PR 提交与每日完成分别记录。

PR 正文必须包含：触发条件、预期/实际、查证的版本、根因与代码位置、排除 YeYu 的对照依据、精简脱敏日志、修复内容、修复前后测试和实际验证限制。不能把“怀疑”“未复现”写成确定原因，也不上传完整运行数据库或私人日志。

Git 对象缺失时修复/重建隔离 checkout；工具不可用时选当前支持的提交方式，不照搬旧环境的临时脚本路径，不绕过安全策略。需要用户登录时说明具体阻塞并保留补丁。
