# 上游修复与 PR

先完成 [每日主流程](../daily-workflow.md) 的版本核实与 [归因](triage.md)，确认是工具缺陷或已授权补全的工具能力缺口，并排除 YeYu 接入错误。仅按实际任务授权对外提交。

**先验证通过，再向上游提交 PR。** 用户于 2026-09-17 明确要求：游戏任务修复或能力补全必须先通过相关测试，并从已安装 WebGUI 的“开始每日”完成针对改动的实机验证，取得对应账号、RunAttempt 的工具终态和日志证据。离线测试、编译、候选构建或启动成功不能替代实机验证。验证未完成、失败或受阻时保留本地候选继续处理，不创建上游 PR，包括草稿 PR；不能以“先开草稿等验证”绕过顺序。已有 PR 的新增修订也应先验证再推送。无游戏运行影响的纯文档改动按其实际影响验证，不要求无关实跑。

1. 查询官方最新 release、默认分支和相关 open/closed issue、PR；记录链接、commit 与查询时间，避免重复修复。
2. 在项目 `.cache` 对应候选目录准备独立上游 checkout，保留已有补丁和用户配置。读取上游 AGENTS、贡献说明及测试要求；不猜默认分支或 fork 所有人。
3. 用最小失败测试/复现固定根因，修改上游源码，运行相关测试。不要把游戏逻辑修复植入 YeYu 观察器；不能靠吞异常或改失败标签获得成功。
4. 检查 diff、依赖/生成物与敏感信息。使用独立分支提交，仅包含这个问题的必要改动；Codex 默认分支前缀为 `codex/`，明确的仓库约定优先。
5. 经正常发布/绑定将候选接入，从 WebGUI 完成改动对应的实机验证，核对终态、配置恢复及完整日志；失败或受阻则回到修复，不进入 PR 步骤。
6. 验证通过后再推送 fork 并向上游创建 PR；已有同一修复 PR 时更新它，避免重复。正文通过结构化参数或 UTF-8 文件传入 `--body-file`，不拼接 Shell 字符串。
7. 核对 PR URL、base/head 和 CI。失败先读日志，处理本次引入的问题；额外未覆盖环境如实列明，不能用限制说明代替本次改动必需的验证。只有已经观察到的审查和 CI 状态可报告。
8. 将已验证的候选版本、实跑证据和 PR 关联写入本机调查记录，继续剩余每日；PR 提交与每日完成分别记录。

修复 PR 正文必须包含：触发条件、预期/实际、查证的版本、根因与代码位置、排除 YeYu 的对照依据、精简脱敏日志、修复内容、修复前后测试和实际验证限制。能力补全 PR 改为说明已查证的缺口、新增入口与默认开关、范围和验证证据，不虚构旧功能缺陷。不能把“怀疑”“未复现”写成确定原因，也不上传完整运行数据库或私人日志。

Git 对象缺失时修复/重建隔离 checkout；工具不可用时选当前支持的提交方式，不照搬旧环境的临时脚本路径，不绕过安全策略。需要用户登录时说明具体阻塞并保留补丁。
