# YeYu Gamer 编排合同

本文定义 YeYu Gamer 与上游游戏工具的接入边界。它描述已授权的编排职责、证据合同和验收层次；不把候选构建、离线回放或工具启动写成游戏任务完成。

## 1. 产品职责与唯一控制面

YeYu Gamer 只负责四件事：

1. 在官方工具运行时追加被动日志、步骤事件和可选截图采集。
2. 将用户在 YeYu Gamer 保存的官方参数与步骤范围临时投影到该工具的官方配置入口。
3. 编排本轮固定工具与已绑定游戏/模拟器的启动、结束和队列交接。
4. 在整轮结束后按游戏、账号和结果发送紧凑邮件，附上可展开的截图报告及本机完整日志查看入口。

Manager 是配置、批次、Run、RunAttempt、Todo 和 artifact 归属的唯一控制面。WebGUI、CLI、Adapter 和外部 Agent 均通过 typed API 读取或提交；不得直接改运行数据库、状态文件或借旧脚本绕过 Manager。

维护者修复 Adapter 协议失败后，可以通过现有 `POST /todo-instances/{id}/transitions` 显式提交 `status=pending`、`releaseTechnicalBlocker=true` 和具体修复原因。Manager 必须验证：仍在当前周期、未完成的常规任务；原 Run 已结束且最新 Attempt 明确 protocolValid=false；当前 Adapter 已验证晋级、摘要不同且仍声明该操作；所有待解除阻塞均属于该失败 Attempt 的技术复核/协议阻塞。人机验证、策略阻塞、其他 Attempt 的阻塞不能借此释放。操作幂等、原子记账，保留原 Run/Attempt 失败、证据和次数，并记录新旧包摘要及发起人；不启动游戏、不修改完成事实。之后仍从“开始每日”创建新尝试。普通 pending 转换不能绕过这项验证。

游戏内识别、条件判断、领奖、重试、恢复和任务成败由上游工具负责。Adapter 不补写 DailyTask、任务节点、OCR 判定或资源判断，也不以截图、窗口、进程退出码或普通日志代替上游终态。工具源码保持官方原样；允许的注入只有 sitecustomize 观察器、配置写后恢复和官方 CLI 启动参数。细则见 [职责与接入规范](yeyu-orchestration-responsibility.md)。

2026-09-08 用户补充授权：普通已保存账号登录确认缺少衔接时可以最小补齐，不应一概转人工。NTE v1.3.11 的官方 `wait_login` 只点底部“进入游戏”，未处理 HOTTA 已保存账号确认弹窗；`NteSavedLogin.py` 在官方任务线程中匹配用户截图提取的三个无账号信息模板，确认前台后在官方 `operate` 输入锁内，只向所属登录弹窗发送一次鼠标点击，记录前后工件及进展，然后仍由官方 `ensure_main` 判定是否进入主界面。不选择账号、不输入凭据、不处理验证码/条款/付费、不新增重试。这个具体衔接不是通用视觉任务框架，上游补齐后应移除该模块与模板。

## 2. 配置、步骤与账号范围

每个游戏保留两类独立数据：

- **今日步骤**：用户明确选择的 Todo 范围。
- **官方参数**：该工具已声明的路线、关卡、队伍、次数或其他配置值。

Adapter 必须逐项追到固定上游版本中的正式配置字段或正式调用点，才可注入或报告该步骤。缺少映射时保留该 Todo 的 `review_required` / `unsupported` 事实，不能合并为别的步骤、暗中追加运行，或把上游根任务成功扩散为子步骤成功。

参数只在本轮固定工具子进程存活期间写入。启动前保存注入字段的原值与恢复依据，确认该子进程结束后只恢复本次注入字段，保留官方对任务进度等其他字段的合法写回；无法确认结束或恢复失败时保留恢复记录，后续运行先恢复，而不让下一账号继承临时配置。省略或 `null` 的参数沿用用户已有官方设置，`false` 是明确关闭。StarRail 的字段恢复与原子写入修复见该工具文档；此规范要求不代表其他工具已完成逐项验收。

多账号游戏按官方工具自己的多账号入口执行。鸣潮启用多个指定账号时，第一个 GameRun 启动官方 `MultiAccountDailyTask`（`--task 7 --exit`）；切号、OCR、登录重试都留在该 task 内。后续指定账号 GameRun 回放该次官方观察与截图，不再第二次启动官方工具。YeYu 不组合 `_switch_to_login`、不改 `done_set`、不给 `ensure_main` 再套一层置前。单账号或当前客户端仍走官方 `DailyTask`（`--task 1 --exit`）。每个账号的页面步骤和官方参数快照仍然保留，用于注入和报告；不得用账号 A 的终态冒充账号 B。

## 3. 运行时观察与结果

观察器只能包装已存在的上游方法，并遵守下列规则：

- 以原参数调用原方法，返回原返回值。
- 原方法抛出的异常必须原样继续抛出。
- 日志、阶段文件或截图写入失败必须 fail-open，不能改变原流程、调用顺序或异常。
- 只有同一游戏、账号、Run、RunAttempt 与游戏日内的明确上游任务终态可参与自动汇总。

新 Adapter 的明确成功使用 `upstream_task_succeeded`，上游明确说明无需执行时使用 `upstream_task_skipped`。没有精确阶段终态时为 `upstream_observation_missing` / `review_required`；进程退出、工具窗口、截图或日志文件存在均只构成运输或诊断证据。

原始上游日志以本轮 artifact 封存，保留 logger 名称、级别、时间、消息与异常文本。截图用于过程说明和邮件附件，不是上游结果的门槛；截图采集失败只在报告中说明缺失。

## 4. 生命周期与邮件

Manager 只启动当前绑定的工具和游戏/模拟器。每个账号每日启动前，按用户授权关闭本批队列内其他已配置游戏，包含开始每日前已经打开的客户端；先请求正常退出，再按准确绑定清理并核验。正常结束或普通失败后关闭当前游戏，最后一个也要收尾。取消、本人登录验证、验证码、条款、付费、抽卡、不明成本、PVP 或无法安全确认关闭时保留现场并停止后续队列。身份不明的进程不得强制结束。

邮件正文按游戏和账号列出完成事项、失败事项及一张主要领取截图。其他步骤截图与诊断摘要放进可展开的 HTML 报告附件；完整原始日志保存在本机 Manager，经证据页读取，当前不会把全部原始日志附进邮件。附件执行归属与哈希校验。截图缺失时照常报告实际结果并注明缺图；SMTP 受理和收件箱送达分别记录，不由构建或离线测试推断。

## 5. 上游来源与候选迁移

每日更新、故障归因与贡献按 [共用每日工作流](../daily-workflow.md) 执行。先核实官方最新版本及已有修复，排除 YeYu 配置、观察与生命周期问题；确认上游缺陷后，可按任务授权在隔离上游源码中修复并提交 PR。这不授权在 Adapter 或运行时观察器中改写官方游戏逻辑。候选来源和本地补丁必须明确标注，修复验证后继续真实每日。

每个接入都固定记录上游仓库、提交或发行版本、正式入口、配置字段和任务方法。需要恢复或迁移上游时，在本机隔离候选中核验来源、文件哈希、依赖和入口；不覆盖现有工具、用户配置或游戏安装目录。上游缺陷优先追踪官方 issue 或 PR，不在 Adapter 中重写游戏逻辑规避。

候选、构建和离线回放只证明来源、协议、配置映射或观察器行为。真实验收必须从已安装 WebGUI 的“开始每日”进入，并取得同轮账号范围内的上游终态、artifact 和整轮报告结果。

## 6. 当前明确限制

以下是当前已知限制，不能在界面或邮件中描述为已解决：

- **鸣潮局部选择**：官方 `DailyTask` 没有七个内部步骤的独立执行入口。只有完整七步集合可调用该日常；局部选择以 `ww_selection_unsupported` 结束，不会偷跑完整日常。体力路线、梦魇布尔和 Additional Tasks 是官方配置开关，不是自编跳过逻辑。
- **星穹铁道日常实训与领奖**：两者共享同一个上游 `daily` 命令，必须成对选择。2026-09-09 实跑后移除没有官方独立终态的私有验证行；原四项官方任务和截图保留，历史验证失败记录不追认为成功。
- **异环每日活跃检查**：官方 v1.3.18 基线缺少 `daily-activity` 的 inspect-only 入口；本机功能候选已补充 `DailyActivityTask`，在 2026-09-17 的已安装 WebGUI 运行中取得 100/100 和有效工具终态（对应日志与运行编号保留本机）。验证后提交的 [上游 PR #326](https://github.com/BnanZ0/ok-nte/pull/326) 尚未合并；该次实跑使用另列的 WGC 依赖修复候选，不能宣称官方发行版已包含此能力。后续修订须重新验证再推送，旧基线的历史未完成结果保持原样。
- **异环 routine .6**：咖啡、影院约会、喷泉签到和异象家具现在已有独立 Todo、官方配置字段投影及 `DailyRoutineTask` 项目终态观察；它们均为默认不选，且只在相应 Todo 被选择时启用。咖啡当前仅允许无补货、无购买、无商品优化的“仅领取收益”官方自动化分支；其它咖啡模式保留为用户配置，但被选中时如实以 `review_required` 报告，不能偷换为成本动作。该接入尚未完成已安装版本的真实每日与邮件验收。
- **真实验收**：离线验证、候选准备和发布后健康检查均已与实机每日区分；本合同不宣称七个游戏或多账号每日已经完成真实整轮运行与邮件验收。

## 7. 接入检查表

`run_progress` 是不属于官方 Todo 的接入操作记录，包含 `operation`、`code`、`message` 和 `metrics`（实际触发来源及等待条件）。它沿相同 RunAttempt、fencing token、事件序列和时间边界校验、存储与展示，不增加 Todo 尝试或完成数。适配器必须在真实发生点发送，不以轮询重复发送冒充进展。

`run_artifact_staged` 复用同一工件导入边界与数量/字节限额，关联本轮选中 Todo 的冻结游戏日，但没有 TodoAttempt。导入后 `diagnosticOnly=true`，不得被 Todo 终态引用为完成证据。它用于任务开始前的接入截图和整轮原始工具日志，避免为保存诊断而伪造任务开始。

PGR 首次资源确认由 `pgr_source_dialog.py` 最小补全：仅在官方运行前刷新 interface 且尚无 TASK_FLOW_START 时，读取配置绑定的唯一 FOS 进程 UI Automation 树；必须同时匹配“确认即将运行的资源”、`overflow65537 / MAA_Punish` 及完整官方仓库地址。使用原确认按钮 InvokePattern，每轮最多调用一次，调用不确定时不重发；通过官方 TASK_FLOW_START 确认交回。前后所属窗口截图分别封存为 integration-source-confirm-before/after，不修改 Security 确认记录、协议、账号或业务任务。当前只核验了 v4.9.5 中文弹窗；上游提供正式非交互确认入口后应迁回官方入口并删除此补全。

启动前的人工要求不能伪造 Todo 开始：`run_terminal` 可选字段 `startupHumanRequiredReason` 仅在 `status=human_required` 且 `attemptedTodoInstanceIds=[]` 时使用，必须是非空的实际官方提示。Manager 将其保留为运行结果原因，沿既有 human_required 生命周期保留客户端。已有步骤的人工要求仍使用原 Todo 终态。普通已保存账号登录继续由已确认的适配补全处理，不使用此字段提前结束。

新增或迁移一个工具时，维护者应留下以下可审查证据：

1. 固定上游来源、版本/提交、许可证和正式启动入口。
2. 每个 Manager 步骤到官方配置字段和调用点的映射，及没有映射的明确记录。
3. 参数快照、临时投影、子进程结束确认与字节恢复的离线回放。
4. 观察器对原返回值、原异常、日志不可写和未调用步骤的回放。
5. Adapter 协议回放，证明任务终态、日志 artifact 和账号/RunAttempt 归属一致。
6. 通过已安装 WebGUI 发起的真实范围验收，以及与该轮结果一致的邮件/附件记录。

前五项不足以宣布游戏每日完成；第六项也只说明所选账号和步骤的那一轮结果。

2026-09-10 验收要求：每次实机验收必须勾选本轮范围内的全部目标游戏（WW、PGR、StarRail、ZZZ、Endfield、GF2、NTE），从已安装 WebGUI 的“开始每日”执行完整队列，保留各账号及原有步骤和配置开关。不能临时缩为单游戏或某个领取步骤来取得通过结果；FGO、BD2、CZN、NIKKE 仍不纳入本轮专项验收。局部离线测试只作故障定位，不能代替整轮验收。已完成项目按 Manager 同游戏日冻结承接规则处理，不删除记录或强制重跑；承接结果和本轮实际执行结果分别列明。每个目标游戏都必须有明确的完成、未完成或无法确认状态及其依据；因更新、人工验证或原有停止规则而未执行的后续游戏不能漏报或算作成功。完整轮次必须有官方子任务终态、未执行项、异常、清理及单次整轮报告的关联证据；不能把启动、进程退出或无日志当作完成。

实机确认：HOTTA 弹窗由 `NTEGame.exe` 的 `Qt51517QWindowToolSaveBitsOwnDC` 窗口承载，直接 owner 是官方工具绑定的 `HTGame.exe` 游戏 HWND。官方底层游戏截图不含弹窗。因此仅对上述唯一可见所属窗口使用 `PrintWindow`；点击前在官方输入锁内重新核对归属、前台和三个模板。用户切到其他窗口时不点击。取消或异常退出时也封存已产生的官方完整日志，不依赖第一个任务成功返回。


健康轮询的 storage=healthy 表示当前存储可读取，不表示刚完成全库完整性审计。/health、/snapshot 和状态版本查询只做轻量元数据读取；完整 PRAGMA quick_check 保留在 /diagnostics，使用独立 mode=ro SQLite 连接读取已提交 WAL 视图，不持有 Manager 的共享写锁，完成后关闭连接。诊断不创建第二写入者，不使用轮询时间冒充任务进展。实际存储异常继续返回统一的 manager_storage_unavailable 错误。


步骤边界一旦被 Manager 受理，就不能因该次截图失败而在较晚终态补拍。截图去重依据同 RunAttempt、TodoAttempt 的已持久化边界事件及已有工件，不能只检查成功图片是否存在。失败保留为独立接入结果；首次直接终态没有更早返回边界时，仍保留该处必要截图。事件重放不重新触发截图 IO。此约定继续使用串行 Adapter worker 与原事件表，不引入第二份截图状态。
